# 01 · 产品定位、技术形态与需求差距

本页描述固定源码快照，不代表本机运行验收。证据编号见 [证据清单](07-evidence-and-corrections.md)。

## 1. 先按用户效果定义比较标准

SessionRelay 的核心不是创建一个“多模型聊天站”，而是连接用户选定的两条**已有会话**，保留原客户端的上下文、工具、工作目录与授权；用户定义谁管理、实施或审查，程序负责已完成结果的暂存、定向交接与状态核对。跨平台、同平台不同会话、三种协作模式和阶段批准门都属于正式需求。[SR01–SR03]

因此，“能注册多个 Agent”“能启动多个模型”“能恢复自身保存的 thread”均不能单独作为产品达标证据。还必须确认目标确为用户选择的原会话，能够识别这次投递的终态和结果，并且不会与原客户端争用或串话。

## 2. LoopX 的实际定位

LoopX 的架构描述了 registry、Goal 状态、运行记录、历史、attention 与 compute quota 六类控制面。它把 Agent、Provider、Capability 与 Kernel 的责任分开，区分观察、验证、接受状态变更和执行。当前仓库还包含协作层、Chat/工作区、平台宿主集成、可选扩展及桌面预览，不宜缩写成“一个不做执行的 Python 脚本”。[LX01、LX03、LX04]

尤其是协作层，任一注册 Agent 可以在一次请求里担任请求方、执行方或协调方；角色是请求关系，不是固定品牌或不可变层级。请求保留父级来源，结论返回直接请求者。**这与 SessionRelay 的平台和角色解耦有实质共通点。** 但注册、在线、具备执行授权和已经接受具体请求仍被分开处理。[LX04]

技术形态也需更新认识：Python 包要求 Python 3.11+，同时控制面包含 TypeScript，并依赖 Node 22.22.3+；DSH 插件是独立 npm 包。桌面目录采用实验性 Tauri 外壳，复用 React 与 HTTP 服务；不是 Electron 的白名单 IPC 架构。[LX01、LX02、LX11]

## 3. 与 SessionRelay 逐项比较

| 用户需要的效果 | LoopX 本轮可见证据 | 对 SessionRelay 的判断 |
|---|---|---|
| 选择现有客户端中的具体会话 | Codex 启动器接受 resume_thread_id；DSH 插件绑定当前活跃原生会话 | 有候选实现，不等于通用历史会话选择器；需客户端版本与并发附着验证 |
| 自定义管理/执行/审查关系 | 请求方、接收方、协调方可以按请求改变 | 值得吸收请求关系模型；不能把 Goal/Agent ID 直接当平台会话 ID |
| 同平台两个会话协作 | 有多 Agent 协作及 DSH 同宿主案例 | 案例每阶段新建执行会话；不能代替两条预先选定旧会话的往返验收 |
| 自动接力、人工干预、管理方主导 | 多类授权、门控、协作请求与回传机制 | 没有证据说明其 UI/语义与本项目三模式一一对应；须做显式适配 |
| 本地暂存、关联与恢复 | 请求、结果、回传路由、attempt 和验证状态分别记录 | 是高价值源码参照，但不能把一个 ACK 当成实际执行完成 |
| 暂停后允许在途收尾 | DSH driver 区分 queued、claimed、admitted | 与本项目相近；其他宿主的 stop/cancel 含义仍要分别核查 |
| 不替代各家聊天客户端 | 原生插件路径可保留宿主；同时也有 LoopX 自管 Chat 运行时 | 只取原生接入部分；不能把自管 Chat 悄悄作为旧会话替代品 |
| 无新 HTTP 监听与系统服务 | 可选桌面壳依赖本地 HTTP 服务 | 整体搬入冲突；小模块提取或受控子进程更合适 |
| 用户批准下一阶段 | Kernel 有治理边界；本项目要求固定阶段审批 | 保留 SessionRelay 的阶段门，不因上游自动化能力扩大授权 |

表中 LoopX 事实对应 LX04–LX12；SessionRelay 基线对应 SR01–SR03。后续是否能部署和稳定运行，全部留在验证计划，不从源码存在直接推导。

## 4. 同平台案例应怎样理解

上游 cross-runtime 用例描述 analyst、builder、reviewer 的多阶段协作和二轮修改，包含产物验证与返回原会话的示例。不过文档明确说明：执行使用 DSH，同一案例每个阶段是新执行会话，由显式控制器推进并用 Git 转移允许的产物；它不是已经实测的 Claude/Codex 跨运行时自主协作。[LX12]

这个案例值得借鉴的是**分工、约束保留、产物版本、返修和交付验证**。它没有替本项目证明“同一个 DSH 客户端中，我事先选好的 A/B 对话持续往返”，更没有证明任意 Codex 桌面对话可安全共享控制。

## 5. 值得加入产品的增强，而非首版功能堆积

以下是研究建议，不是已批准需求：

- 交接中显示“接收方已收到 / 已采纳 / 正在执行 / 已给结论 / 结论已送达”，避免所有状态压成一个“完成”。可借鉴协作 receipt/read model，映射到现有状态，不另造任务库。[LX04、LX07、LX08]
- 审查固定产物版本：交接引用提交、摘要或快照；修改后形成新结果版本，显示审查结论针对哪个版本。[LX06、LX07]
- 管理方有界派工：指定角色只能对已绑定会话发出允许的动作，不能新增执行权限、扩大收件人范围或解除暂停。这是将上游关系模型收敛到本项目两节点场景的设计建议。
- 额度受限时由用户替换角色绑定，并移交任务摘要和产物版本；未决投递先核对，不直接把旧结果送入新绑定。软件预算、账号实际余额和平台共享限制必须分别显示，不虚构剩余额度。

不建议首版同时引入长期 Goal 图、飞书、远程工作区、账户路由、自动更新、市场扩展和完整 Chat UI。只有它们能解决已经确认的需求时，才扩大范围。

## 6. 产品判断

**LoopX 是功能重叠但控制边界不同的候选底座，不是一个已证明能替代 SessionRelay 的成品。** 当前最有把握的收益是局部协议、校验和宿主事件处理复用；整体替换要把“原会话身份不变、用户控制不变、执行权限不扩大”作为先决条件，而不是后补细节。
