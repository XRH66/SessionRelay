# 06 · 有界验证计划与下一执行会话交接

**本页是待执行计划，不是测试报告或开发授权。** 本轮未安装依赖、未调用模型、未向原会话发消息、未启动 P1。既有 [phases.md](../../phases.md) 保持权威；本页只建议把下一步研究收敛到能做出明确决策的实验。

## 1. 继承现有成果，不再从零建库

使用最新 GitHub/本地同步状态，先读项目规则、ProjectContext、architecture、platform-contracts、phases，再读本研究目录。记录实际基线，注意本研究的固定提交不等于运行时最新版本。

当前 P1 已要求三模式、双向往返、会话互斥、防重、两类审批与暂停恢复，不重复添加一套同名计划。先通过接入门，再实现这些要求。[SR01–SR04]

## 2. 实验 A：Codex 原会话完成链

### 输入与权限

用户明确选择一条已有测试会话，授权一条无副作用的有界消息及结果回读。记录版本、入口和脱敏身份。不同意安装、改配置或起新后台服务时，不把这些动作作为暗中前置。启动独立 app-server 进程是否允许，也应在实验授权中说清楚。

### 操作顺序

1. 只读确认目标身份、可访问状态与现有运行轮次；不要依据标题猜会话。
2. 从既有证据选一条路线：queue + 可关联回读，或原线程 resume + turn/start。两条路线分别留证，不拼接证明。
3. 发前保存 delivery、原绑定与唯一测试标记；经暂停/占用门后只发一次。
4. 保存平台返回的 message/turn/request ID；等待原生终态，再回读本轮 final 输出。
5. 核对目标仍为原 thread，结果确属本次投递，桌面端上下文与显示一致；检查是否发生新建/fork/clone 或线程竞争。
6. 验证中途暂停不再新增投递，在途结果可以暂存；结果读取失败时保持明确未验证状态。

### 通过与停止

PASS：原会话身份保持、这次发送与终态/最终结果有可重复核对的关联、没有未经授权的权限变化或替代会话。FAIL：附着冲突、目标变化、只有发送回执无对应结果、缺少可信身份或未知接受状态。失败后停止并列出缺哪一环，不通过换成新会话达标，不自动重发。

LoopX 的 RPC/事件实现可减少客户端代码摸索，但不能替此实验出具结果。优先使用 host 原生字段建立关联；正文随机标记仅辅助诊断，不独自作为永久关联协议。

## 3. 实验 B：DSH 原生能力到外部适配器

### 第一段：只读能力确认

核对用户当前 DSH 与插件 API 版本，沿现有 MCP/CLI 查找可用会话枚举。区分活跃 Agent 列表、全部历史会话、已恢复的当前会话。验证列表中的稳定身份可与用户已选会话对应。

对照 LoopX driver 中 ctx.agents.list/get 与原生事件，确认宿主是否已导出同类能力。若已有可用工具，直接复用；不要为参考代码重新写一个完整控制插件。

### 第二段：仅在缺入口且获批后验证窄桥

窄桥只提供枚举/检查/提交/订阅终态所需的受限能力，与现有宿主工具共用真实逻辑；不得导出任意 shell、平台数据库写入或凭据。优先复用已有认证通道；不默认新开 SessionRelay HTTP 服务。

一次有界投递需对上 sessionId、现有 request_id、原生 message/turn/source 和最终输出。验证人工插话、非本桥来源、旧 Session 对象与恢复/清空会话的行为。来源未知时显示 partial/unsupported，不假装能自动检测所有人工输入。

PASS：外部 SessionRelay 候选接口能操作原会话并关联结果。仅在宿主内看见事件、只有 active agent 枚举或只执行了 LoopX 示例，都不能写成完整通过。

## 4. 实验 C：小范围 TypeScript 提取评估

此实验在批准后只需离线 fixture，不调用模型。

1. 从 semantic_request.ts 开始列出直接/传递导入，明确要复用的函数和上游许可。
2. 保留现有 SessionRelay 信封，建立显式映射；不要把 LoopX receiver decision 混成阶段 decision。
3. 将纯校验与宿主 IO 分开，使同一函数供 CLI、UI、IPC 调用。
4. 加入缺字段、超长输入、绝对/越界路径、错误身份、旧 revision、重复请求、结果冲突等用例。
5. 对 result_publication 的更新链进行 fixture 验证：同内容重放不重复；不同内容不覆盖；未确认前序投递时后序不越过。
6. 记录抽离后的依赖、改动和维护面，再决定直接复用、移植或保留自研。不因它是 TS 就默认零成本。

## 5. 最小接力与反例矩阵

A/B 接入验证通过后才执行原计划中的真实 A→B→A。可以分别在新旧路径测试，但不得用新会话路径替代原会话验收。

| 场景 | 必须观察的行为 |
|---|---|
| 正常完成 | 明确平台终态、最终回复、正确 task/stage/revision、唯一关联 |
| failed/interrupted/审批等待 | 不冒充 completed，不自动进入下一阶段 |
| 重复完成通知/回读同一结果 | 复用已存结果，不新增重复 forward |
| 发出后 receipt 丢失 | 标 unknown，核对原请求，不盲重发 |
| forward 已 sending 但源仍待转发 | 查原 forward，不新建第二条绕过去 |
| pause 与 submit 竞争 | 发送前门有线性顺序；已发起按在途处理 |
| 人工编辑后批准 | 批准绑定编辑后的具体载荷版本；旧批准失效 |
| 用户在原客户端插话 | 能识别则暂停；不能识别则明确限制，不混成模型结果 |
| 换平台/会话/角色 | revision 改变；旧结果不进入新绑定 |
| 同平台两条旧会话 | A/B 身份不同、互不串话、拒绝自连接 |
| 同会话换入口或跨组使用 | 同一原生会话不得因入口不同绕过占用锁 |
| 账号额度不足/认证失效 | 停止该投递，显示实际错误；不擅自换账号/计费路线 |
| 产物变化后审查 | 审查固定版本；变化触发重新核验，不沿用旧通过 |
| 模型声明批准/恢复/扩权 | 不改变用户批准门，不扩大平台权限 |
| 退出与重开 | 先核对在途与回执，保持暂停，不自动重放 |

这些是本研究建议新增或细化的验收，不是声称上游已经跑过本项目全部场景。

## 6. 对 P1 顺序的建议

不新增大型阶段体系。把上述 A/B 作为 P1 接入前置的两个有终点检查点，C 作为纯模块抽离试验；通过后继续既有 P1。完整同平台产品验收仍可放 P4，但适配器和数据模型从 P1 起不得强制两边品牌不同。

manager_driven 的现有文字混用了“指定主导角色”和“手工触发”。实现前需明确：管理方在用户已批准范围内的普通派工是否允许自动投递。建议允许受控 manager proposal 通过程序校验，但阶段通过、暂停解除与权限扩展仍需用户决定；这是澄清建议，不在本次直接改动正式规格。
